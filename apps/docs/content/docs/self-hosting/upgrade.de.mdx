Ciele wird als getaggte Releases veröffentlicht. Jedes Release ist ein einzelner
Commit im öffentlichen Repository plus ein `vMAJOR.MINOR.PATCH`-Tag, sodass die
Frage „Welche Version führe ich aus?“ immer eine genaue Antwort hat:

```sh
git describe --tags
```

Verknüpfen Sie Ihre Bereitstellung mit einem Tag, anstatt den Standard-Branch zu
verfolgen, und Sie entscheiden, wann Sie wechseln möchten.

## Aktualisieren einer Docker-Bereitstellung

```sh
git fetch --tags
git checkout v0.2.0        # the release you want
docker compose -f deploy/docker-compose.yml up -d --build
```

Dadurch wird das App-Image neu erstellt und der Stack neu gestartet. Der
`migrate`-Dienst wird zuerst ausgeführt, wendet nur die Migrationen an, die Sie
noch nicht haben, und beendet sich; die App startet, sobald dies abgeschlossen
ist. Sie führen Migrationen nicht manuell aus.

Wenn Sie das [Workers-Profil](/self-hosting/workers) aktiviert haben, baut
`--build` auch diese Images neu – es ist kein separater Schritt erforderlich.

## Aktualisieren einer Quellbereitstellung

Direktes Ausführen der Apps statt in Compose:

```sh
git fetch --tags && git checkout v0.2.0
pnpm install
pnpm build
```

Wenden Sie ausstehende Migrationen auf Ihre Datenbank an, bevor Sie den neuen
Build starten – unter [Database](/self-hosting/database) erfahren Sie, wie der
nach Dateinamen sortierte Runner funktioniert und wie er verfolgt, was er
bereits angewendet hat.

## Erstellen Sie zuerst ein Backup

Ein Upgrade, das Migrationen anwendet, ändert Ihr Schema. Erstellen Sie jedes
Mal einen Dump, bevor Sie beginnen:

```sh
docker compose -f deploy/docker-compose.yml exec -T postgres \
  pg_dump -U postgres postgres | gzip > ciele-$(date +%F).sql.gz
```

Zwei Volumes enthalten alles, was wichtig ist: `postgres-data` (die Datenbank)
und `storage-data` (hochgeladene Dateien). Sichern Sie beide – ein reiner
Datenbank-Dump stellt Ihre Assistenten, Konversationen und Wissensdatensätze
wieder her, aber nicht die Dateien, die dahinter stehen.

<Callout type="warn" title="Migrations move forward only">
There is no down-migration path. Rolling back to an earlier version means
restoring the backup you took before the upgrade, not re-running the runner in
reverse. This is why the dump above is not optional.
</Callout>

## Wiederherstellen

```sh
docker compose -f deploy/docker-compose.yml down
git checkout v0.1.0
gunzip -c ciele-2026-07-25.sql.gz | docker compose -f deploy/docker-compose.yml \
  exec -T postgres psql -U postgres postgres
docker compose -f deploy/docker-compose.yml up -d --build
```

Stellen Sie den Dump wieder her, der der Version entspricht, auf die Sie
zurücksetzen möchten. Ein neuerer Dump enthält ein neueres Schema, das der
ältere Code nicht versteht.

## Was Sie vor einem kleineren Upgrade lesen sollten

Versionshinweise werden zu jedem Tag veröffentlicht und weisen auf alles hin,
was eine Entscheidung Ihrerseits erfordert – eine neue erforderliche
Umgebungsvariable, eine geänderte Standardeinstellung, eine Migration, die eine
große Tabelle neu schreibt. Überfliegen Sie sie, bevor Sie eine Bereitstellung
aktualisieren, auf die andere angewiesen sind. Patch-Releases sind Routine,
kleinere Releases gelegentlich nicht.
