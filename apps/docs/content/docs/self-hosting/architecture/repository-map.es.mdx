## Cómo dependen los espacios de trabajo entre sí

El grafo de dependencias es superficial a propósito. Ningún elemento compartido
depende de una aplicación, y el paquete de datos no depende de nada interno en
absoluto, lo que permite que su suite de pruebas se ejecute de forma aislada.

`packages/charts` lo consume la consola de operaciones administrada, que está
fuera del árbol de código abierto; se incluye en el espacio de trabajo, pero
nada en una descarga de código abierto lo importa.

## Dentro de la aplicación web

La aplicación se organiza en capas de forma limpia: las rutas pasan por un
gestor de datos con ámbito de solicitud, las mutaciones se canalizan a través de
un único control de autorización y todo lo generativo se encuentra detrás del
módulo de tiempo de ejecución.

<Mermaid
  title="Capas dentro de apps/web"
  chart={`
flowchart TB
  MW["middleware.ts + lib/auth.ts<br/>session gate — who is this?"]

  MW --> RSC["Server Components<br/>app/(admin)/** — reads"]
  MW --> ACT["Server Actions<br/>app/actions.ts — writes"]
  MW --> API["Route handlers<br/>app/api/** — chat · cron"]

  ACT --> AZ["lib/authz.ts + lib/rbac.ts<br/>may they do this?"]
  API --> RT["lib/runtime/<br/>chat · retrieval · crawling · jobs"]
  ACT --> RT

  RSC --> DATA["lib/data.ts<br/>request-scoped data handle"]
  AZ --> DATA
  RT --> DATA
  DATA --> PG[("Postgres<br/>row-level security")]
`}
/>

De esta forma se derivan tres propiedades que vale la pena conocer antes de
cambiar nada:

- **There is no client-side write path.** Los navegadores invocan acciones del
  servidor; las acciones del servidor realizan mutaciones. Añadir una mutación
  significa añadir una acción, no un punto de conexión.
- **Every organization-scoped mutation starts at one guard.** La comprobación de
  autorización es una única función, por lo que cambiar el modelo de rol afecta
  a dos archivos en lugar de a cada sitio de llamada.
- **Reads carry the caller's identity into Postgres**, por lo que se les aplica
  seguridad a nivel de fila. El aislamiento de inquilinos se aplica tanto en la
  base de datos como en la aplicación.

## Dónde reside el peso

Los números que aparecen a continuación proceden de un análisis estático del
propio código fuente de la aplicación —símbolos y las importaciones y llamadas
entre ellos— agregados por área. Son una medida aproximada de lo conectada que
está cada área, lo que es un buen indicador de «cuánto del sistema se verá
afectado si cambio esto».

| Área | Conectividad relativa | Qué hay allí |
|---|---:|---|
| `lib/runtime/` | ●●●●●●●●●● | Enrutamiento, acciones, recuperación, rastreo, incrustaciones, tareas |
| `components/ui/` | ●●●●● | Primarias compartidas, utilizadas desde cualquier lugar |
| `components/assistant/` | ●● | El editor del asistente: general, conocimiento, flujos, publicar |
| `app/actions.ts` | ●● | Todas las mutaciones del producto, en un solo archivo |
| `app/(admin)/` | ●● | Las páginas de la consola |
| `app/api/` | ● | Puntos de conexión de widget, vista previa y cron |

Dos entradas merecen un comentario. `lib/runtime/` es, con mucho, la parte más
densa de la base de código: es donde reside casi todo el comportamiento, y
precisamente por eso su superficie pública está bloqueada. Y `app/actions.ts` es
el *archivo* más conectado: es una costura deliberada y no un accidente, ya que
una superficie de mutación es lo que hace verificable que «cada mutación esté
autorizada».

<Callout title="Reproducing this yourself">
Any call-graph tool over `apps/web/src` will show the same shape. The point of
the table is the ordering, not the exact figures — treat it as a map of where to
tread carefully.
</Callout>
