## L'applicazione in breve

Inizia da qui. Questa è l'intera applicazione in un'unica immagine: tutti i
principali sottosistemi e la direzione in cui viaggiano le richieste attraverso
di essi. Ogni livello sottostante è trattato in una delle pagine di questa
sezione.

<Mermaid
  title="L'applicazione, livello per livello"
  chart={`
flowchart TB
  S["<b>Surfaces</b><br/>chat widget · admin console · embed and iframe"]
  E["<b>Request handling</b><br/>session gate → server components (reads)<br/>server actions (writes) · route handlers (chat · cron)"]
  G["<b>Authorization</b><br/>role → capability · one guard for every write"]
  R["<b>Chat runtime</b><br/>flow router · action registry · agentic search"]

  D["<b>Data layer</b><br/>one interface · two implementations"]

  X["<b>External</b><br/>AI providers · sites you crawl · email · ticketing"]

  S --> E --> G --> R
  E --> D
  R --> K
  R --> O
  R --> D
  K --> D
  O --> D
  D --> P
  R --> X
  K --> X
  O --> X
`}
/>

Leggilo dall'alto verso il basso. **Surfaces** sono le uniche cose che un
browser tocca. **Request handling** separa le letture dalle scritture: le pagine
leggono, le azioni scrivono e i gestori di route trasportano la chat e il lavoro
pianificato. **Authorization** è un unico guardiano attraverso il quale passa
ogni scrittura a livello di organizzazione. Le bande **chat runtime**,
**knowledge** e **operations** sono il cuore del comportamento. Tutto raggiunge
Postgres attraverso un'unica interfaccia del **livello dati**, mai direttamente.

Ciò che il diagramma omette è altrettanto informativo di ciò che mostra. Nessuna
superficie raggiunge da sola il runtime o il database, nulla scrive senza
passare attraverso il guard e solo le tre bande centrali comunicano con il mondo
esterno.

## L'intera distribuzione, in un'unica immagine

Questo è il software. Ecco cosa esegui effettivamente: un'applicazione Next.js,
un database Postgres e una manciata di job pianificati. Tutto il resto è
facoltativo.

L'applicazione è volutamente noiosa da gestire: è un server Next.js standard,
non mantiene alcuno stato proprio e tutti i dati persistenti risiedono in
Postgres. Scala l'applicazione eseguendo più copie.

## I processi

| Processo | Descrizione | Obbligatorio |
|---|---|---|
| **Web app** | La console di amministrazione, il widget di chat pubblica e l'API HTTP, in un'unica applicazione Next.js | Sì |
| **Postgres** | Ogni riga di dati persistenti, con sicurezza a livello di riga e pgvector per il recupero | Sì |
| **Scheduled jobs** | Endpoint HTTP sotto `/api/cron/*` richiamati con un timer — finalizzazione della scansione, sweep di ripetizione della scansione, esportazioni, rollup dell'utilizzo, controlli degli obiettivi | Consigliato |
| **Docs site** | Questa documentazione, un'app Next.js separata | No |
| **Workers** | Container sotto `services/` per crawling più pesante e lavoro sui grafi | No |

Lo [stack Docker Compose](/self-hosting/installation) collega i primi tre per
impostazione predefinita e lascia i worker dietro un profilo opt-in.

## Due limiti imposti dagli strumenti

La maggior parte del codebase è costituita da normale codice applicativo che
puoi leggere dall'inizio alla fine. Due moduli sono diversi: la loro interfaccia
pubblica è vincolata, quindi puoi farci affidamento e modificare tutto ciò che
sta dietro.

<Mermaid
  title="I due confini dei moduli imposti"
  chart={`
flowchart TB
  UI["Console pages · API routes<br/>server actions"]

  subgraph rt["Chat runtime"]
    direction TB
    RTB["Two entry points:<br/>server barrel · client barrel"]
    RTI["Internals: router, actions,<br/>retrieval, crawlers, embeddings"]
    RTB --> RTI
  end

  subgraph db["Data layer"]
    direction TB
    DBI["One interface<br/>every query in the app"]
    IMPL1["Postgres"]
    IMPL2["In-memory"]
    DBI --> IMPL1
    DBI --> IMPL2
  end

  UI --> RTB
  UI --> DBI
  RTI --> DBI
  UI -.->|"lint error"| RTI
`}
/>

- **The data layer** è un'interfaccia con due implementazioni. Quella reale
  comunica con Postgres con sicurezza a livello di riga; quella in memoria
  consente all'intera applicazione di avviarsi senza alcun database, ed è così
  che funziona un nuovo checkout senza alcuna configurazione. Una suite di test
  condivisa viene eseguita su entrambi, quindi non possono deviare.
- **The chat runtime** espone esattamente due entry point — un server barrel e
  un client-safe barrel — e una regola lint rifiuta le importazioni che li
  superano. Un test blocca la superficie esportata, quindi ampliarla è un'azione
  intenzionale e non un incidente.

Entrambi i confini esistono per lo stesso motivo: sono le parti che hanno
maggiori probabilità di essere sostituite e quelle in cui una perdita si
propagherebbe più lontano.
