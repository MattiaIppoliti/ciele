Cette section s'adresse aux personnes qui exécutent Ciele sur leur propre
infrastructure ou qui modifient son code. Elle décrit le déploiement tel qu'il
est réellement : quels processus existent, avec quoi chacun communique et où se
situent les limites. Les pages de fonctionnalités de la [Documentation](/)
principale décrivent ce que fait le produit ; ces pages décrivent comment il est
construit.

<Callout title="Read the code when the two disagree">
These diagrams are maintained alongside the source, but the source is the
authority. Every page names the files it describes so you can check.
</Callout>

## L'application en un coup d'œil

Commencez ici. Voici l'application entière en une seule image : tous les
sous-systèmes principaux et la direction dans laquelle les requêtes les
traversent. Chacune des couches ci-dessous fait l'objet d'une page dans cette
section.

<Mermaid
  title="L'application, couche par couche"
  chart={`
flowchart TB
  S["<b>Surfaces</b><br/>chat widget · admin console · embed and iframe"]
  E["<b>Request handling</b><br/>session gate → server components (reads)<br/>server actions (writes) · route handlers (chat · cron)"]
  G["<b>Authorization</b><br/>role → capability · one guard for every write"]

  O["<b>Operations</b><br/>publishing · insights and exports · improvements and alerts"]
  D["<b>Data layer</b><br/>one interface · two implementations"]
  P[("<b>Postgres + pgvector</b><br/>row-level security")]
  X["<b>External</b><br/>AI providers · sites you crawl · email · ticketing"]

  S --> E --> G --> R
  E --> D
  R --> K
  R --> O
  R --> D
  K --> D
  O --> D
  D --> P
  R --> X
  K --> X
  O --> X
`}
/>

Lisez-le de haut en bas. **Surfaces** sont les seuls éléments qu'un navigateur
touche. **Request handling** sépare les lectures des écritures : les pages
lisent, les actions écrivent et les gestionnaires de route transportent le chat
et le travail planifié. **Authorization** est un garde par lequel passe chaque
écriture à l'échelle de l'organisation. Les bandes **chat runtime**,
**knowledge** et **operations** sont le lieu où réside le comportement. Tout
arrive à Postgres via une interface unique de **couche de données** — jamais
directement.

Ce que le diagramme omet est aussi instructif que ce qu'il montre. Aucune
surface n'atteint le runtime ou la base de données par elle-même, rien n'écrit
sans passer par le garde, et seules les trois bandes du milieu communiquent avec
le monde extérieur.

## L'ensemble du déploiement, en une seule image

C'est le logiciel. Voici ce que vous exécutez réellement : une application
Next.js, une base de données Postgres et quelques tâches planifiées. Tout le
reste est facultatif.

L'application est délibérément banale à utiliser : c'est un serveur Next.js
standard, elle ne conserve aucun état propre, et toutes les données durables
sont stockées dans Postgres. Faites-la évoluer en exécutant davantage
d'instances.

## Les processus

| Processus | Ce que c'est | Requis |
|---|---|---|
| **Web app** | La console d'administration, le widget de chat public et l'API HTTP, dans une seule application Next.js | Oui |
| **Postgres** | Chaque ligne de données durables, avec sécurité au niveau de la ligne et pgvector pour la récupération | Oui |
| **Scheduled jobs** | Points de terminaison HTTP sous `/api/cron/*` appelés par une minuterie — finalisation de l'analyse, balayages de réanalyse, exportations, cumul de l'utilisation, vérifications des objectifs | Recommandé |
| **Docs site** | Cette documentation, une application Next.js distincte | Non |
| **Workers** | Conteneurs sous `services/` pour un crawling plus lourd et un travail sur les graphes | Non |

La [pile Docker Compose](/self-hosting/installation) relie les trois premiers
par défaut et laisse les workers derrière un profil optionnel.

## Deux limites imposées par l'outil

La majeure partie du code source est du code d'application ordinaire que vous
pouvez lire de haut en bas. Deux modules sont différents : leur surface publique
est imposée, vous pouvez donc vous y fier et modifier tout ce qui se trouve
derrière.

<Mermaid
  title="Les deux limites de module imposées"
  chart={`
flowchart TB
  UI["Console pages · API routes<br/>server actions"]

  subgraph rt["Chat runtime"]
    direction TB
    RTB["Two entry points:<br/>server barrel · client barrel"]
    RTI["Internals: router, actions,<br/>retrieval, crawlers, embeddings"]
    RTB --> RTI
  end

  subgraph db["Data layer"]
    direction TB
    DBI["One interface<br/>every query in the app"]
    IMPL1["Postgres"]
    IMPL2["In-memory"]
    DBI --> IMPL1
    DBI --> IMPL2
  end

  UI --> RTB
  UI --> DBI
  RTI --> DBI
  UI -.->|"lint error"| RTI
`}
/>

- **The data layer** est une interface avec deux implémentations. La véritable
  interface communique avec Postgres avec une sécurité au niveau des lignes ;
  l'interface en mémoire permet à l'ensemble de l'application de démarrer sans
  aucune base de données, ce qui explique comment une nouvelle extraction
  s'exécute sans aucune configuration. Une suite de tests partagée s'exécute sur
  les deux, ce qui empêche toute dérive.
- **The chat runtime** expose exactement deux points d'entrée — un « barrel »
  serveur et un « barrel » sécurisé client — et une règle Lint rejette les
  importations qui les dépassent. Un test verrouille la surface exportée, de
  sorte que son élargissement est un acte délibéré plutôt qu'un accident.

Ces deux limites existent pour la même raison : ce sont les parties les plus
susceptibles d'être remplacées et celles où une fuite se propagerait le plus
loin.
