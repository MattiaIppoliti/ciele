## Comment les espaces de travail dépendent les uns des autres

Le graphe de dépendances est volontairement peu profond. Aucun élément partagé
ne dépend d'une application, et le paquet de données ne dépend d'aucun élément
interne, ce qui permet à sa suite de tests de s'exécuter de manière isolée.

`packages/charts` est consommé par la console d'opérations gérée, qui se trouve
en dehors de l'arborescence open source ; il est fourni dans l'espace de
travail, mais rien dans une extraction open source ne l'importe.

## À l'intérieur de l'application Web

L'application est organisée en couches de manière claire : les routes passent
par un gestionnaire de données au niveau de la requête, les mutations sont
canalisées par un seul garde d'autorisation, et tout ce qui est génératif se
trouve derrière le module d'exécution.

<Mermaid
  title="Couches à l'intérieur d'apps/web"
  chart={`
flowchart TB
  MW["middleware.ts + lib/auth.ts<br/>session gate — who is this?"]

  MW --> RSC["Server Components<br/>app/(admin)/** — reads"]
  MW --> ACT["Server Actions<br/>app/actions.ts — writes"]
  MW --> API["Route handlers<br/>app/api/** — chat · cron"]

  ACT --> AZ["lib/authz.ts + lib/rbac.ts<br/>may they do this?"]
  API --> RT["lib/runtime/<br/>chat · retrieval · crawling · jobs"]
  ACT --> RT

  RSC --> DATA["lib/data.ts<br/>request-scoped data handle"]
  AZ --> DATA
  RT --> DATA
  DATA --> PG[("Postgres<br/>row-level security")]
`}
/>

Trois propriétés découlent de cette structure, et il est utile de les connaître
avant de modifier quoi que ce soit :

- **There is no client-side write path.** Les navigateurs appellent des actions
  serveur ; les actions serveur effectuent des mutations. Ajouter une mutation
  signifie ajouter une action, et non un point de terminaison.
- **Every organization-scoped mutation starts at one guard.** La vérification
  d'autorisation est une fonction unique ; par conséquent, la modification du
  modèle de rôle concerne deux fichiers plutôt que chaque site d'appel.
- **Reads carry the caller's identity into Postgres**, la sécurité au niveau des
  lignes leur est donc appliquée. L'isolement des locataires est appliqué aussi
  bien dans la base de données que dans l'application.

## Où se situe le poids

Les chiffres ci-dessous proviennent d'une analyse statique du code source de
l'application — des symboles ainsi que des importations et des appels entre eux
— agrégés par domaine. Ils constituent une mesure approximative du degré de
connexion de chaque domaine, ce qui est un bon indicateur pour savoir « quelle
part du système sera affectée si je modifie ceci ».

| Domaine | Connectivité relative | Ce qu'il contient |
|---|---:|---|
| `lib/runtime/` | ●●●●●●●●●● | Routage, actions, récupération, exploration, intégrations, tâches |
| `components/ui/` | ●●●●● | Primitives partagées, utilisées partout |
| `components/assistant/` | ●● | L'éditeur de l'assistant : général, connaissances, flux, publication |
| `app/actions.ts` | ●● | Chaque mutation du produit, dans un seul fichier |
| `app/(admin)/` | ●● | Les pages de la console |
| `app/api/` | ● | Points de terminaison du widget, de la prévisualisation et de la tâche cron |

Deux éléments méritent d'être commentés. `lib/runtime/` est de loin la partie la
plus dense du code source : c'est là que se trouve la quasi-totalité du
comportement, et c'est précisément pour cette raison que sa surface publique est
verrouillée. Et `app/actions.ts` est le *fichier* le plus connecté : il s'agit
d'une articulation délibérée plutôt que d'un accident, car c'est une surface de
mutation unique qui permet de vérifier que « chaque mutation est autorisée ».

<Callout title="Reproducing this yourself">
Any call-graph tool over `apps/web/src` will show the same shape. The point of
the table is the ordering, not the exact figures — treat it as a map of where to
tread carefully.
</Callout>
