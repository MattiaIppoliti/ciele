## Wie die Workspaces voneinander abhängen

Der Abhängigkeitsgraph ist absichtlich flach. Nichts, was gemeinsam genutzt
wird, hängt von einer Anwendung ab, und das Datenpaket hängt von überhaupt
nichts Internem ab – was es ermöglicht, seine Testsuite isoliert auszuführen.

`packages/charts` wird von der verwalteten Operations-Konsole genutzt, die sich
außerhalb des Open-Source-Baums befindet. Sie wird im Workspace bereitgestellt,
aber nichts in einem Open-Source-Checkout importiert sie.

## Innerhalb der Webanwendung

Die Anwendung ist sauber in Schichten unterteilt: Routen lesen über einen
Data-Handle im Request-Bereich, Mutationen laufen durch einen einzigen
Authorisierungs-Guard, und alles Generative befindet sich hinter dem
Runtime-Modul.

<Mermaid
  title="Layers innerhalb von Apps/Web"
  chart={`
flowchart TB
  MW["middleware.ts + lib/auth.ts<br/>session gate — who is this?"]

  MW --> RSC["Server Components<br/>app/(admin)/** — reads"]
  MW --> ACT["Server Actions<br/>app/actions.ts — writes"]
  MW --> API["Route handlers<br/>app/api/** — chat · cron"]

  ACT --> AZ["lib/authz.ts + lib/rbac.ts<br/>may they do this?"]
  API --> RT["lib/runtime/<br/>chat · retrieval · crawling · jobs"]
  ACT --> RT

  RSC --> DATA["lib/data.ts<br/>request-scoped data handle"]
  AZ --> DATA
  RT --> DATA
  DATA --> PG[("Postgres<br/>row-level security")]
`}
/>

Aus dieser Form ergeben sich drei Eigenschaften, die Sie kennen sollten, bevor
Sie etwas ändern:

- **There is no client-side write path.** Browser rufen Server-Aktionen auf;
  Server-Aktionen führen Mutationen durch. Das Hinzufügen einer Mutation
  bedeutet, eine Aktion hinzuzufügen, keinen Endpunkt.
- **Every organization-scoped mutation starts at one guard.** Die
  Autorisierungsprüfung ist eine einzelne Funktion. Wenn Sie also das
  Rollenmodell ändern, betrifft dies nur zwei Dateien und nicht jede
  Aufrufstelle.
- **Reads carry the caller's identity into Postgres**, daher gilt für sie
  Sicherheit auf Zeilenebene. Die Mandantenisolierung wird sowohl in der
  Datenbank als auch in der Anwendung erzwungen.

## Wo das Gewicht liegt

Die folgenden Zahlen stammen aus einer statischen Analyse des Quellcodes der
Anwendung – der Symbole sowie der Importe und Aufrufe zwischen ihnen –
aggregiert nach Bereichen. Sie sind ein grobes Maß dafür, wie stark die
einzelnen Bereiche miteinander verbunden sind, was wiederum ein guter Indikator
dafür ist, „wie viel vom System es bemerken wird, wenn ich dies ändere“.

| Bereich | Relative Vernetzung | Was dort lebt |
|---|---:|---|
| `lib/runtime/` | ●●●●●●●●●● | Routing, Aktionen, Abruf, Crawling, Einbettungen, Jobs |
| `components/ui/` | ●●●●● | Gemeinsam genutzte Primitives, die von überall verwendet werden |
| `components/assistant/` | ●● | Der Assistent-Editor: Allgemein, Wissen, Flows, Veröffentlichen |
| `app/actions.ts` | ●● | Jede Mutation im Produkt, in einer Datei |
| `app/(admin)/` | ●● | Die Seiten der Konsole |
| `app/api/` | ● | Widget-, Vorschau- und Cron-Endpunkte |

Zwei Einträge verdienen einen Kommentar. `lib/runtime/` ist mit großem Abstand
der dichteste Teil der Codebasis – hier befindet sich fast das gesamte
Verhalten, und genau deshalb ist seine öffentliche Oberfläche gesperrt. Und
`app/actions.ts` ist die am stärksten vernetzte einzelne *Datei*: Es handelt
sich um eine bewusste Schnittstelle und nicht um einen Zufall, da eine einzige
Mutationsoberfläche die Überprüfung ermöglicht, ob „jede Mutation autorisiert
ist“.

<Callout title="Reproducing this yourself">
Any call-graph tool over `apps/web/src` will show the same shape. The point of
the table is the ordering, not the exact figures — treat it as a map of where to
tread carefully.
</Callout>
