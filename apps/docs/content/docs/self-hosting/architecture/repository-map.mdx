<Callout title="Enterprise code is not in an open-source checkout">
A small set of managed-service features lives under dedicated paths that are
removed when the public tree is assembled, so an open-source checkout simply does
not contain them — nor the database migrations that belong to them. See
[The open-core boundary](/self-hosting/open-core-boundary).
</Callout>

## How the workspaces depend on each other

The dependency graph is shallow on purpose. Nothing shared depends on an
application, and the data package depends on nothing internal at all — which is
what lets its test suite run in isolation.

<Mermaid
  title="Workspace dependencies (arrows point at the dependency)"

  DOCS["apps/docs<br/>documentation site"]

  WEB --> DB
  WEB --> UI
  DOCS --> UI

`packages/charts` is consumed by the managed operations console, which is outside
the open-source tree; it ships in the workspace but nothing in an open-source
checkout imports it.

## Inside the web application

The application layers cleanly: routes read through a request-scoped data handle,
mutations funnel through a single authorization guard, and everything generative
sits behind the runtime module.

<Mermaid
  title="Layers inside apps/web"
  chart={`
flowchart TB
  MW["middleware.ts + lib/auth.ts<br/>session gate — who is this?"]

  MW --> RSC["Server Components<br/>app/(admin)/** — reads"]
  MW --> ACT["Server Actions<br/>app/actions.ts — writes"]
  MW --> API["Route handlers<br/>app/api/** — chat · cron"]

  ACT --> AZ["lib/authz.ts + lib/rbac.ts<br/>may they do this?"]
  API --> RT["lib/runtime/<br/>chat · retrieval · crawling · jobs"]
  ACT --> RT

  RSC --> DATA["lib/data.ts<br/>request-scoped data handle"]
  AZ --> DATA
  RT --> DATA
  DATA --> PG[("Postgres<br/>row-level security")]
`}
/>

Three properties follow from this shape, and they are worth knowing before you
change anything:

- **There is no client-side write path.** Browsers call server actions; server
  actions mutate. Adding a mutation means adding an action, not an endpoint.
- **Every organization-scoped mutation starts at one guard.** The authorization
  check is a single function, so changing the role model touches two files rather
  than every call site.
- **Reads carry the caller's identity into Postgres**, so row-level security
  applies to them. Tenant isolation is enforced in the database as well as in the
  application.

## Where the weight sits

The numbers below come from a static analysis of the application's own source —
symbols and the imports and calls between them — aggregated per area. They are a
rough measure of how connected each area is, which is a good proxy for "how much
of the system will notice if I change this".

| Area | Relative connectedness | What lives there |
|---|---:|---|
| `lib/runtime/` | ●●●●●●●●●● | Routing, actions, retrieval, crawling, embeddings, jobs |
| `components/ui/` | ●●●●● | Shared primitives, used from everywhere |
| `components/assistant/` | ●● | The assistant editor: general, knowledge, flows, publish |
| `app/actions.ts` | ●● | Every mutation in the product, in one file |
| `app/(admin)/` | ●● | The console's pages |
| `app/api/` | ● | Widget, preview, and cron endpoints |

Two entries deserve comment. `lib/runtime/` is by a wide margin the densest part
of the codebase — it is where nearly all behaviour lives, which is exactly why its
public surface is locked. And `app/actions.ts` is the single most connected
*file*: it is a deliberate seam rather than an accident, since one mutation
surface is what makes "every mutation is authorized" checkable.

<Callout title="Reproducing this yourself">
Any call-graph tool over `apps/web/src` will show the same shape. The point of
the table is the ordering, not the exact figures — treat it as a map of where to
tread carefully.
</Callout>
