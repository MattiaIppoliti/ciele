modifican su código. Describe la implementación tal y como es en realidad: qué

## La aplicación de un vistazo

Empieza aquí. Esta es la aplicación completa en una imagen: todos los
subsistemas principales y la dirección en la que viajan las solicitudes a través
de ellos. Cada capa que aparece a continuación es el tema de una de las páginas
de esta sección.

<Mermaid
  title="La aplicación, capa por capa"
  chart={`
flowchart TB
  S["<b>Surfaces</b><br/>chat widget · admin console · embed and iframe"]
  E["<b>Request handling</b><br/>session gate → server components (reads)<br/>server actions (writes) · route handlers (chat · cron)"]
  G["<b>Authorization</b><br/>role → capability · one guard for every write"]
  R["<b>Chat runtime</b><br/>flow router · action registry · agentic search"]
  K["<b>Knowledge</b><br/>ingestion jobs · crawler matrix · chunking and embeddings"]
  O["<b>Operations</b><br/>publishing · insights and exports · improvements and alerts"]
  D["<b>Data layer</b><br/>one interface · two implementations"]
  P[("<b>Postgres + pgvector</b><br/>row-level security")]
  X["<b>External</b><br/>AI providers · sites you crawl · email · ticketing"]

  S --> E --> G --> R
  E --> D
  R --> K
  R --> O
  R --> D
  K --> D
  O --> D
  D --> P
  R --> X
  K --> X
  O --> X
`}
/>

Léelo de arriba abajo. **Surfaces** son lo único que toca un navegador.
**Request handling** separa las lecturas de las escrituras: las páginas leen,
las acciones escriben y los controladores de rutas llevan el chat y el trabajo
programado. **Authorization** es un guardián por el que pasa cada escritura con
ámbito de organización. Las bandas **chat runtime**, **knowledge** y
**operations** son donde reside el comportamiento. Todo llega a Postgres a
través de una única interfaz de **capa de datos**, nunca directamente.

Lo que el diagrama omite es tan informativo como lo que muestra. Ninguna
superficie llega por sí sola al tiempo de ejecución o a la base de datos, nada
escribe sin pasar por el guardián y solo las tres bandas del medio se comunican
con el mundo exterior.

## Toda la implementación, en una imagen

Ese es el software. Esto es lo que realmente ejecutas: una aplicación Next.js,
una base de datos Postgres y unos cuantos trabajos programados. Todo lo demás es
opcional.

La aplicación es deliberadamente aburrida de operar: es un servidor Next.js
estándar, no mantiene ningún estado propio y todos los datos duraderos residen
en Postgres. Escálala ejecutando más copias.

## Los procesos

| Proceso | Qué es | Requerido |
|---|---|---|
| **Web app** | La consola de administración, el widget de chat público y la API HTTP, en una sola aplicación Next.js | Sí |
| **Postgres** | Cada fila de datos duraderos, con seguridad a nivel de fila y pgvector para su recuperación | Sí |
| **Scheduled jobs** | Puntos de conexión HTTP en `/api/cron/*` invocados por un temporizador: finalización de rastreo, barridos de rastreo repetido, exportaciones, acumulación de uso, comprobaciones de objetivos | Recomendado |
| **Docs site** | Esta documentación, una aplicación Next.js independiente | No |
| **Workers** | Contenedores bajo `services/` para un rastreo más intenso y trabajo con grafos | No |

La [pila de Docker Compose](/self-hosting/installation) conecta los tres
primeros de forma predeterminada y deja a los trabajadores detrás de un perfil
de inclusión voluntaria.

## Dos límites que impone el conjunto de herramientas

La mayor parte de la base de código es código de aplicación ordinario que puedes
leer de principio a fin. Dos módulos son diferentes: su superficie pública está
restringida, por lo que puedes confiar en ella y cambiar todo lo que hay detrás.

<Mermaid
  title="Los dos límites de módulo impuestos"
  chart={`
flowchart TB
  UI["Console pages · API routes<br/>server actions"]

  subgraph rt["Chat runtime"]
    direction TB
    RTB["Two entry points:<br/>server barrel · client barrel"]
    RTI["Internals: router, actions,<br/>retrieval, crawlers, embeddings"]
    RTB --> RTI
  end

  subgraph db["Data layer"]
    direction TB
    DBI["One interface<br/>every query in the app"]
    IMPL1["Postgres"]
    IMPL2["In-memory"]
    DBI --> IMPL1
    DBI --> IMPL2
  end

  UI --> RTB
  UI --> DBI
  RTI --> DBI
  UI -.->|"lint error"| RTI
`}
/>

- **The data layer** es una interfaz con dos implementaciones. La real se
  comunica con Postgres con seguridad a nivel de fila; la que está en memoria
  permite que toda la aplicación arranque sin base de datos, que es como se
  ejecuta una nueva copia de la fuente sin ninguna configuración. Una suite de
  pruebas compartida se ejecuta en ambos, por lo que no pueden desviarse.
- **The chat runtime** expone exactamente dos puntos de entrada —un barril de
  servidor y un barril seguro para el cliente— y una regla de lint rechaza las
  importaciones que los superen. Una prueba bloquea la superficie exportada, por
  lo que ampliarla es un acto deliberado y no un accidente.

Ambos límites existen por la misma razón: son las partes con más probabilidades
de ser reemplazadas y aquellas en las que una fuga se extendería más.
