Chaque octet durable réside dans Postgres. Il existe une quarantaine de tables,
et presque toutes sont rattachées à l'une des deux ancres suivantes : une
**organisation** ou un **assistant**. Apprenez ces deux piliers et le reste du
schéma suivra.

Les deux chaînes se rejoignent au niveau de la récupération plutôt que par le
biais d'une clé étrangère : un fragment est résolu en son concept et sa source,
et ceux-ci deviennent les citations d'un message (voir
[Knowledge pipeline](/self-hosting/architecture/knowledge-pipeline)).

Les lignes de contenu utilisent une clé primaire de type texte court plutôt
qu'un UUID. C'est pourquoi l'identifiant d'un assistant est lisible et copiable
dans la console. Les tables d'organisation, de membre et d'invitation utilisent
des UUID Postgres.

## Comment les locataires restent séparés

L'isolement est appliqué deux fois, délibérément. L'application vérifie les
capacités avant une mutation, et la base de données refuse les lignes
extérieures à l'organisation de l'appelant, quelle que soit la demande de
l'application.

<Mermaid
  title="Deux portes indépendantes sur la même ligne"
  chart={`
flowchart TB
  REQ["A request"]
  APP{"Application:<br/>does this role have<br/>the capability?"}
  SQL{"Postgres:<br/>is the caller a member<br/>of this row's organization?"}
  ROW[("The row")]
  NO1["Rejected in the action"]
  NO2["Invisible to the query"]

  REQ --> APP
  APP -->|"no"| NO1
  APP -->|"yes"| SQL
  SQL -->|"no"| NO2
  SQL -->|"yes"| ROW
`}
/>

La sécurité au niveau des lignes est activée pour chaque table. Les membres
peuvent lire au sein de leur organisation, les éditeurs et les rôles supérieurs
peuvent créer et mettre à jour, et les administrateurs et les rôles supérieurs
peuvent supprimer. Les écritures qui ne doivent pas être falsifiables — un
compteur monotone, par exemple — passent par des fonctions qui s'exécutent avec
des droits élevés plutôt que par une politique qui devrait faire confiance à
l'appelant.

Les fonctions d'assistance appelées par les politiques se trouvent dans un
schéma privé, et non dans le schéma public. Elles ne font donc pas partie de
l'interface API exposée par la base de données.

### Secrets

Deux types de valeurs sont chiffrées par l'application avant d'atteindre
Postgres : les clés API des fournisseurs et les identifiants d'intégration de la
billetterie. Elles sont scellées avec un chiffrement authentifié utilisant une
clé de l'environnement, de sorte que la base de données ne contient jamais que
du texte chiffré et qu'une copie de la base de données ne divulgue pas les
informations d'identification.

<Callout title="Set the encryption key before storing any credential">
The key comes from configuration, not from the database. Rotating it without
re-sealing existing rows makes them unreadable — see
[Configuration](/self-hosting/configuration).
</Callout>

## Comment le schéma est appliqué

Les migrations sont de simples fichiers SQL appliqués dans l'ordre des noms de
fichiers. Elles ne sont **pas** appliquées manuellement, ni avec la commande
push de la CLI Supabase : l'historique en direct de ce projet a été en partie
écrit hors bande, avec des noms et des préfixes numériques en double que
l'historique à clé de version de la CLI ne peut pas représenter.

<Mermaid
  title="L'applicateur de migration"
  chart={`
flowchart TB
  START["Run the applier<br/>against a database URL"]
  LOCK["Take an advisory lock<br/>so concurrent runs are safe"]
  LIST["List migration files<br/>in filename order"]
  BASE{"Listed in the<br/>baseline file?"}
  RECORD["Record it without running it"]
  LEDGER{"Already in<br/>the ledger?"}
  SKIP["Skip"]
  TX["Run it in its own transaction —<br/>which also writes the ledger row"]
  FAIL["Failed: no ledger row,<br/>so the next run retries it"]
  EE["Then the enterprise chain,<br/>where one exists"]

  START --> LOCK --> LIST --> BASE
  BASE -->|"yes"| RECORD
  BASE -->|"no"| LEDGER
  LEDGER -->|"yes"| SKIP
  LEDGER -->|"no"| TX
  TX -->|"error"| FAIL
  TX --> EE
`}
/>

Les propriétés qui comptent sur le plan opérationnel :

- **The ledger is keyed by filename**, dans un schéma privé. Ce qui a été
  exécuté est un fait dans la base de données, et non une hypothèse.
- **Each migration is its own transaction**, et cette transaction écrit la ligne
  du registre. Une migration qui échoue ne laisse aucune trace ; par conséquent,
  une nouvelle exécution de l'appliquer relance exactement la même opération.
- **Concurrent runs are safe**, via un verrouillage consultatif et une nouvelle
  vérification à l'intérieur de la transaction.
- **New migrations use a timestamp prefix** et se retrouvent dans la même
  modification que le code qui en a besoin.
- **The enterprise chain, where present, is applied strictly after the whole
  open-source chain** et utilise le même registre. Une extraction open source ne
  dispose pas d'un tel répertoire et applique uniquement la chaîne open source.

Consultez [Database](/self-hosting/database) pour exécuter ceci sur votre propre
Postgres.
