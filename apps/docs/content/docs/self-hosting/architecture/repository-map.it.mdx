## Come le aree di lavoro dipendono l'una dall'altra

Il grafo delle dipendenze è volutamente poco profondo. Nessun elemento condiviso
dipende da un'applicazione e il pacchetto di dati non dipende da nulla di
interno, il che consente alla sua suite di test di essere eseguita in modo
isolato.

<Mermaid
  title="Dipendenze dell'area di lavoro (le frecce puntano alla dipendenza)"

`packages/charts` viene utilizzato dalla console delle operazioni gestite, che
si trova al di fuori dell'albero open source; viene fornito nel workspace ma non
viene importato da nessun elemento in un checkout open source.

## All'interno dell'applicazione web

L'applicazione è strutturata in modo pulito: le route leggono attraverso un
gestore di dati nell'ambito della richiesta, le mutazioni passano attraverso un
unico guard di autorizzazione e tutto ciò che è generativo si trova dietro il
modulo di runtime.

<Mermaid
  title="Livelli all'interno di app/web"
  chart={`
flowchart TB
  MW["middleware.ts + lib/auth.ts<br/>session gate — who is this?"]

  MW --> RSC["Server Components<br/>app/(admin)/** — reads"]
  MW --> ACT["Server Actions<br/>app/actions.ts — writes"]
  MW --> API["Route handlers<br/>app/api/** — chat · cron"]

  ACT --> AZ["lib/authz.ts + lib/rbac.ts<br/>may they do this?"]
  API --> RT["lib/runtime/<br/>chat · retrieval · crawling · jobs"]
  ACT --> RT

  RSC --> DATA["lib/data.ts<br/>request-scoped data handle"]
  AZ --> DATA
  RT --> DATA
  DATA --> PG[("Postgres<br/>row-level security")]
`}
/>

Da questa struttura derivano tre proprietà che vale la pena conoscere prima di
apportare qualsiasi modifica:

- **There is no client-side write path.** I browser chiamano le azioni del
  server; le azioni del server eseguono le mutazioni. Aggiungere una modifica
  significa aggiungere un'azione, non un endpoint.
- **Every organization-scoped mutation starts at one guard.** Il controllo di
  autorizzazione è una singola funzione, quindi la modifica del modello di ruolo
  interessa due file anziché ogni sito di chiamata.
- **Reads carry the caller's identity into Postgres**, quindi la sicurezza a
  livello di riga si applica a loro. L'isolamento del tenant viene applicato sia
  nel database che nell'applicazione.

## Dove si concentra il peso

I numeri riportati di seguito provengono da un'analisi statica del codice
sorgente dell'applicazione — simboli, importazioni e chiamate tra di essi —
aggregati per area. Sono una misura approssimativa di quanto ogni area sia
connessa, il che è un buon indicatore di "quanta parte del sistema se ne
accorgerà se cambio questo".

| Area | Connessione relativa | Cosa c'è lì |
|---|---:|---|
| `lib/runtime/` | ●●●●●●●●●● | Routing, azioni, recupero, crawling, incorporamenti, job |
| `components/ui/` | ●●●●● | Primitive condivise, utilizzate ovunque |
| `components/assistant/` | ●● | L'editor dell'assistente: generale, conoscenza, flussi, pubblicazione |
| `app/actions.ts` | ●● | Ogni modifica al prodotto, in un unico file |
| `app/(admin)/` | ●● | Le pagine della console |
| `app/api/` | ● | Endpoint per widget, anteprima e cron |

Due voci meritano un commento. `lib/runtime/` è di gran lunga la parte più densa
del codebase: è qui che risiede quasi tutto il comportamento, ed è proprio per
questo che la sua superficie pubblica è bloccata. E `app/actions.ts` è il
singolo *file* più connesso: si tratta di una scelta deliberata, non di un caso,
poiché una singola superficie di mutazione è ciò che rende verificabile
l'affermazione "ogni mutazione è autorizzata".

<Callout title="Reproducing this yourself">
Any call-graph tool over `apps/web/src` will show the same shape. The point of
the table is the ordering, not the exact figures — treat it as a map of where to
tread carefully.
</Callout>
