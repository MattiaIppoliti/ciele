Ciele speichert seine Daten in **Postgres** und nutzt
[Supabase](https://supabase.com) für die Datenbank, die Authentifizierung und
die Sicherheit auf Zeilenebene. Jede Abfrage wird durch Sicherheitsrichtlinien
auf Zeilenebene auf die Organisation des angemeldeten Benutzers beschränkt. So
bleiben die Mandanten voneinander isoliert.

## Bereitstellung

Sie können die Datenbank auf zwei Arten ausführen:

- **Locally**, mit dem gebündelten Stack: `pnpm db:start` bootet Postgres, Auth
  und RLS in Docker, und `pnpm db:reset` wendet das Schema und die Seed-Daten
  an. Dies ist der schnellste Weg, um gegen eine echte Datenbank zu entwickeln.
  Siehe [Installation](/self-hosting/installation).
- **Hosted**, mit einem von Ihnen erstellten Supabase-Projekt. Legen Sie die URL
  und die Schlüssel als Umgebungsvariablen fest (siehe
  [Konfiguration](/self-hosting/configuration)), und die App stellt beim
  nächsten Start eine Verbindung her.

## So werden Migrationen angewendet

Das Schema befindet sich in `supabase/migrations` als geordnete SQL-Dateien.
Migrationen werden von einem kleinen Runner (`scripts/apply-migrations.sh`)
angewendet, der jede ausstehende Datei **in der Reihenfolge der Dateinamen**
ausführt und nach Dateinamen aufzeichnet, was er angewendet hat. Neue
Migrationen verwenden ein Zeitstempel-Präfix, sodass die Reihenfolge eindeutig
ist, und sie landen neben dem Code, der sie benötigt.

<Callout title="Filename-ordered, not CLI-tracked">
The runner tracks applied migrations by filename rather than relying on a CLI's
version history. Follow the same timestamp-prefixed naming for any migration you
add, and let the runner apply it — do not hand-edit the applied ledger.
</Callout>

## Seed-Daten

`supabase/seed.sql` enthält neutrale Demodaten – eine generische Organisation
und einige Beispielassistenten –, sodass eine neue Datenbank nicht leer ist. Sie
können es bedenkenlos auf eine Entwicklungsdatenbank anwenden oder überspringen,
um einen sauberen Produktionsstart zu gewährleisten.

## Die Enterprise-Kette

Das Open-Source-Schema ist völlig eigenständig. Die verwaltete Edition verfügt
über eine zusätzliche Migrationskette, die **nicht Teil des Open-Source-Baums**
ist und niemals von einer selbst gehosteten Bereitstellung erstellt wird. Dies
ist die Datenbankseite der [Open-Core-Grenze](/self-hosting/open-core-boundary):
Enterprise-Tabellen können auf Open-Source-Tabellen verweisen, niemals
umgekehrt.
