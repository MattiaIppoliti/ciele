# Self-host database: the Supabase OSS services over a pluggable Postgres

The open-source map (*Wayfinder map: open-source edition + managed offering*, in the private tracker) decided at charting that the self-host edition runs on the self-hosted Supabase OSS stack via Docker, "no data-layer rewrite", and the Railway map scoped out "replacing Supabase Postgres/auth". Both held. Then institutions started asking to run Ciele on the Postgres they already pay for and audit: Azure Database for PostgreSQL, AWS RDS/Aurora, GCP Cloud SQL/AlloyDB, Neon. The bring-your-own Postgres map charted the way (September 2026).

**Decision.** The self-host stack keeps GoTrue, PostgREST and storage-api as containers and makes the Postgres under them pluggable: `./deploy/bootstrap.sh --database-url postgresql://admin:password@host:5432/db` lists an overlay that parks the `postgres` container, adds a one-shot `provision` service that recreates what the `supabase/postgres` image bakes in at first init, and points the three services and the migration applier at the external host over TLS. The data layer (`packages/db` on PostgREST + RPC, RLS as the tenancy line, the migration chain) is unchanged. This amends the two earlier decisions for the self-host half only; the hosted product's database is not in scope.

**Rejected.**

- **Convex, or any non-Postgres backend.** Not a swap: no SQL, no RLS, a different vector search. The ~68 RPC functions (job claims, idempotency, turn ledger), 277 policies, the migration chain and its CI replay gate would all be discarded. A second `Db` adapter of that size is a rewrite of the product's persistence, not a deployment option.
- **A direct-driver rewrite of `packages/db`** (pg/Drizzle) with pluggable auth (Auth.js/better-auth) and S3 storage, dropping the three services. It removes every Supabase dependency, and it costs months for the same user-visible outcome, moves 277 policies' worth of tenancy into application code, and rebuilds the pglite contract harness. Nothing a self-hoster asked for needs it.
- **Hosted Supabase as the external database for the containers.** Its roles exist with passwords the customer does not hold, `supautils` reserves them from `ALTER`/`GRANT`, and its own GoTrue/PostgREST/Storage own the `auth` and `storage` schemas. Blocked by construction; the sensible variant is pointing the *app* at that project with no `db` profile at all, which is a documentation question, not a mode.

**What the image guaranteed, and who guarantees it now.** The `supabase/postgres` image's init scripts create the roles (`anon`, `authenticated`, `service_role` with `BYPASSRLS`, `authenticator`, `supabase_auth_admin`, `supabase_storage_admin`), the `auth`/`storage`/`extensions` schemas, the `auth.uid()`/`auth.role()` helpers every policy calls, default privileges in `public` for the API roles (which is why the chain never grants table access), the `pgrst_ddl_watch` event triggers that reload PostgREST after DDL, and a `supautils` allowlist that lets the non-superuser `postgres` create extensions and set `pgrst.*` on a role. GoTrue creates neither its schema nor the helpers; storage-api creates its schema but its role installer needs superuser. A managed Postgres has none of that and no superuser. So:

- `deploy/external-db/provision.sql`, run by the `provision` service as the provider's admin, recreates the roles, schemas, owners, helpers, default privileges, the applier's memberships and the two extensions, idempotently.
- `scripts/apply-migrations.sh` ends with `NOTIFY pgrst, 'reload schema'` itself, on every database including the image.
- `20260902090000_postgrest_aggregates.sql` tolerates the refusal of `alter role ... set pgrst.*`; the compose passes the option as an environment variable.

**Requirements, chosen rather than discovered.** Postgres 16 or newer, because on 15 only a superuser may create a `BYPASSRLS` role, and the admin must hold `BYPASSRLS` itself (Azure 16+, Neon and the RDS/Aurora/Cloud SQL/AlloyDB master users do). `service_role` **must** bypass RLS: the service key's reads assume it and the RPC fast paths on `auth.role() = 'service_role'` assume the rows are visible. Making `service_role` the owner of every table instead was considered and deferred: it is a chain-wide ownership decision, not a bootstrap line. The direct endpoint, never a pooler: PostgREST and storage-api hold a `LISTEN` connection and GoTrue's migrations rely on the role's `search_path`. Storage stays on the `file` backend; the files are then the one thing pinning the stack to its host, and the recovery runbook says so.

**Consequences.**

- Two Postgres 16 facts shape the provisioner and are pinned by `packages/db/src/testing/external-db-provision.test.ts`: the creator of a role holds `ADMIN OPTION` but not `SET`, so the admin is granted membership *before* `create schema ... authorization`; and `public` belongs to `pg_database_owner`, so the admin must own the database.
- The self-host CI job validates the overlay with `docker compose config`; the migrations gate gains a second leg on plain `postgres:16` + pgvector so provider-neutrality is asserted, not hoped.
- `deploy/compose.test.mjs` runs the real `bootstrap.sh --database-url` and locks what it writes and what it refuses (pooler hostnames, hosted Supabase, `sslmode=disable`, unencoded URL characters).
- The Desktop wizard does not offer this yet; it reads the same `.env` the flag writes, so a "Database" step is a fresh effort with a defined contract, not a redesign.
